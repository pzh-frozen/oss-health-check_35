# 用「五看三定」为 oss-health-check 做一次战略体检

> 本文是《开源文化运动》期末项目的战略分析部分。它要回答三个具体问题：
> 一个由学生维护、只有一个人写代码的小工具，在开源世界里**凭什么存在**、
> **往哪里走**、**怎么走到那里**。
>
> 方法上采用华为的「五看三定」：先通过**看行业/趋势、看市场/客户、看竞争、看自己、
> 看机会**洞察战略机会点，再通过**定战略控制点、定目标、定策略**把机会转成可落地的规划。

## 0. 分析边界与假设

战略分析最怕两件事：一是把"我想做什么"当成"市场需要什么"，二是用不可验证的数字
撑场面。因此先把边界讲清楚：

| 维度 | 设定 |
| --- | --- |
| 分析对象 | `oss-health-check`（本仓库），一个零依赖的开源项目健康度检查 CLI |
| 团队规模 | 1 名维护者（学生），每周可投入约 10 小时，零预算 |
| 时间窗口 | 2026 年 4 月 - 2027 年 3 月，按季度滚动复盘 |
| 数据来源 | 公开资料与行业报告、GitHub 上与同类工具的观察、课程内 20 位同学的非正式访谈 |
| 数字口径 | 凡标注「估算」的均为自下而上的粗略推算，用于判断量级而非精确预测 |

需要说明的是：本文的结论不是"这个项目会成功"，而是"在资源极度受限的前提下，
哪些方向值得投入、哪些必须主动放弃"。

## 1. 五看

### 1.1 看行业与趋势：开源从"开发方式"变成"基础设施"

过去十年，开源完成了从"理想主义协作"到"现代软件供应链底座"的身份转变。今天的应用
几乎不可能不依赖开源组件，这使得"依赖是否健康"从工程师的个人判断，上升为供应链安全
与合规问题。几个可以观察到的结构性变化：

**（1）合规从自愿走向强制。** 欧盟《网络弹性法案》（CRA）对含数字元素的产品提出
安全维护、漏洞处理与 SBOM 要求，过渡期在 2027 年前后收尾；OpenChain ISO 5230 把
开源合规流程标准化；国内信通院、开放原子开源基金会也在推动开源治理与 SBOM 相关规范。
合规压力会顺着供应链向下传导，最终落到每一个仓库的 README、LICENSE 与 SECURITY.md 上。

**（2）度量体系已经成熟。** CHAOSS 社区定义了活跃度、多样性、成熟度等指标族；
OpenSSF Scorecard 给出了 18 项可自动化的安全检查；GitHub 自带 Community Profile
提示社区文件齐全度；LFX Insights 面向基金会与企业提供项目健康看板。这说明"给开源项目
打分"不再是新鲜概念，而是被验证过的需求。

**（3）AI 编码改变了供需结构。** 代码产量上升、人工评审能力相对下降，使得自动化的
规范检查比过去更有价值——人不再有时间逐行看"这个仓库有没有贡献指南"。

**（4）教学场景正在放量。** 越来越多高校开设开源课程、参与开源之夏与校园行，
课程作业天然需要"可量化、可解释、可批量"的评价方式。

**趋势判断**：行业的主旋律已经从"鼓励大家开源"转向"证明你的开源是健康的"。
度量工具处在上升期，但通用维度已被大厂与基金会占据，**新进入者的机会在细分场景，
而不在"做一个更全的 Scorecard"**。

对本项目的直接含义：不要和 Scorecard 比覆盖面，要比"在某个具体场景里更好用"。

### 1.2 看市场与客户：谁真的会为一个检查器买单

工具类项目的客户不是"所有开发者"，而是"某个时刻被某个问题卡住的人"。按使用场景拆开：

| 角色 | 典型场景 | 真实痛点 | 现有替代 | 付费/使用意愿 |
| --- | --- | --- | --- | --- |
| 学生 | 课程项目提交前自查 | 不知道评分点，凭感觉补文档 | 老师给的清单、同学互看 | 高（免费即可） |
| 教师 / 助教 | 一个学期审 80-150 个仓库 | 逐个人工看 README、LICENSE 耗时且标准不一 | Excel + 抽查 | 高（能省时间就行） |
| 个人开发者 | 项目首次开源前体检 | 不知道还缺什么，怕被说"不专业" | 搜索引擎、凭经验 | 中 |
| 中小团队 | 给自家仓库或依赖做初筛 | 商业 SCA 太贵，Scorecard 需联网且结果难解释 | Scorecard、人工审计 | 中 |
| 企业 OSPO | 供应商开源合规初筛 | 流程重、工具贵、报告要能对内解释 | 商业 SCA、LFX | 低（短期不碰） |

把需求特征提炼出来，会发现四个关键词反复出现：**轻**（不要装一堆依赖）、
**快**（一条命令出结果）、**可解释**（告诉我为什么扣分、怎么改）、**可离线**
（内网、无 GitHub 访问的环境也能用）。这四个词恰好对应本项目的技术选择：
零依赖、单命令、逐项建议、纯本地扫描。

**市场容量估算（自下而上，仅判断量级）**：假设一所高校每学期有 100 个课程项目需要
自查，全国有 100 所高校在开类似课程，一年两个学期，则仅教学场景每年就有约 2 万次
扫描需求；再叠加个人开发者与团队的长尾，量级在每年数万到十万次。这个数字不足以支撑
一门生意，但足以支撑一个"被真实使用的小工具"——而这正是本项目的定位。

**客户结论**：把教学场景作为第一个闭环，把个人开发者作为自然增长来源，暂时放弃
企业市场（销售与合规成本远超单人团队的能力边界）。

### 1.3 看竞争：通用市场已被占据，细分市场仍然空白

| 工具 | 覆盖维度 | 部署方式 | 中文支持 | 可解释性 | 可定制 | 主要短板 |
| --- | --- | --- | --- | --- | --- | --- |
| OpenSSF Scorecard | 18 项安全/工程检查 | 需联网 + Token，CLI/Action | 弱 | 中（有逐项说明） | 低 | 面向 GitHub 仓库，偏安全，结果偏"评分"少"建议" |
| GitHub Community Profile | 社区文件齐全度 | 平台内置 | 有界面 | 低（只有有无） | 无 | 不可定制、不可门禁 |
| CHAOSS 指标 | 活跃度/多样性/成熟度 | 自行采集 | 弱 | 高（学术化） | 高 | 工程门槛高，非开箱即用 |
| LFX Insights | 项目健康看板 | SaaS | 有 | 中 | 低 | 面向基金会/企业，学生用不上 |
| RepoReaper | 是否废弃 | 研究脚本 | 无 | 低 | 低 | 单一维度 |
| 自研脚本 / Excel | 取决于作者 | 本地 | 有 | 低 | 高 | 不可复用、无社区 |

竞争格局可以一句话概括：**"全"的市场有巨头，"中文 + 教学 + 可解释"的市场几乎没有
像样的供给**。Scorecard 是最强的潜在替代者，但它有三道门槛：需要网络与权限、
输出面向安全工程师、英文语境。短期内它不会为"课程作业"这个场景做优化。

需要警惕的是"降维打击"：如果 GitHub 在 Community Profile 里加入可配置的权重与
建议生成，本项目的差异化会被压缩。应对方式不是堆功能，而是把根扎在**教学场景的
工作流**里（作业模板、批量扫描、教师视角的汇总报告），这是平台不会做的脏活。

### 1.4 看自己：能力盘点与 SWOT

**资源盘点**

| 已有 | 仍然缺少 |
| --- | --- |
| 13 个检查项、可配置权重、三种输出 | 远程仓库扫描（`--repo owner/name`） |
| 35 个测试、CI 三版本矩阵、覆盖率统计 | 插件机制（第三方检查项） |
| 五类社区文档、issue/PR 模板、行为准则 | 批量扫描与教师端汇总报告 |
| MIT 许可证、语义化版本、变更日志 | 社区规模与推广渠道 |
| 中文文档与「五看三定」战略分析 | 可持续的维护人力 |

**SWOT**

| | 有利 | 不利 |
| --- | --- | --- |
| **内部** | **S**：零依赖、可离线、可解释、中文原生、权重可配置、工程质量尚可（测试 + CI） | **W**：单人维护、检查偏表层（文件是否存在）、无远程扫描、无界面、社区为 0 |
| **外部** | **O**：合规趋严、中文治理工具缺口、教学场景放量、AI 时代对自动化治理的需求 | **T**：Scorecard/GitHub 功能扩张、同类学生项目同质化、课程结束后项目停滞 |

**关键差距**：真正的短板不是"检查项不够多"，而是**可持续性**——一个人写、一个人维护、
一个人回答 issue，任何一次期末周都可能让项目停摆三个月。这决定了战略必须优先解决
"降低维护成本"和"让别人愿意接手"，而不是"再加十个检查项"。

### 1.5 看机会：把趋势翻译成可执行的机会点

| 编号 | 机会点 | 依据 | 吸引力 | 可行性 | 结论 |
| --- | --- | --- | --- | --- | --- |
| O1 | 教学场景标准化：作业模板 + 批量评分 | 课程需求确定、决策链短、教师就是用户 | 高 | 高 | **主打** |
| O2 | 中文开源治理工具缺口 | 现有工具英文为主，中文文档稀缺 | 中高 | 高 | **主打** |
| O3 | GitHub Action / PR 评论，进入日常工作流 | CI 是开发者必经之路，集成成本低 | 高 | 中 | 第二优先 |
| O4 | 与 Scorecard 互操作（读它的 JSON、输出可转换） | 借生态而非对抗 | 中 | 中 | 探索 |
| O5 | 企业 OSPO 供应商初筛 | 合规预算充足 | 高 | 低（销售、法务、信任门槛） | 暂缓 |
| O6 | 开源治理内容品牌（教程、案例库） | 内容能反哺工具信任 | 中 | 高 | 长期投入 |

**机会窗口**：CRA 过渡期与国内开源治理规范的落地集中在未来 12-18 个月；教学场景则有
固定的学期节律（3-6 月、9-12 月两个峰值）。这意味着**每年两次"获客窗口"**，
发布节奏应当与之对齐。

## 2. 三定

### 2.1 定战略控制点：做"中文教学场景的开源健康度标准"

战略控制点不是"我有什么功能"，而是"别人短期抄不走、且能持续带来注意力与资源的位置"。
候选方案与评估如下：

| 候选控制点 | 可复制性 | 壁垒强度 | 与自身能力匹配 | 判断 |
| --- | --- | --- | --- | --- |
| A. 检查项数量最多 | 高（照抄即可） | 低 | 中 | 放弃 |
| B. 中文教学场景的评分标准与案例库 | 低（需长期积累与信任） | 高 | 高 | **主控制点** |
| C. 深度绑定 CI（Action + SARIF + 门禁） | 中 | 中 | 中 | 辅助控制点 |
| D. 开源治理内容品牌 | 中 | 中高 | 中 | 长期辅助 |

**选择 B 为主、C 为辅**，理由有三：

1. **场景是护城河**。检查项可以被复制，但"某门课程用它作为作业自查工具、教师用它的
   汇总报告评分"这种工作流嵌入，复制成本极高。
2. **中文是天然壁垒**。国际工具没有动力为中文教学场景做本地化与模板适配，而这是
   本项目成本最低的差异化。
3. **控制点必须可积累**。评分规则、案例库、课程模板都会随时间变厚；而"功能更多"
   只会随时间被追平。

围绕 B 构建壁垒的路径：

- **规范化**：把 13 项检查的判定规则、权重理由写成公开的评分白皮书，让"为什么 85 分"
  可以被讨论、被引用；
- **案例库**：积累 100 个真实仓库的评分与"改进前后对比"，形成可检索的教学素材；
- **课程合作**：与 2-3 门课程共建作业模板，把工具嵌进教学流程；
- **插件生态**：允许第三方以 entry points 提供检查项，让标准由社区共同维护。

### 2.2 定目标：从"能跑"到"被采用"

**使命**：让每一个开源项目都能用最低成本完成一次诚实的健康体检。
**愿景**：成为中文开源课程与中文开发者社区默认的自检工具。
**价值观**：可解释优于全面，透明优于权威，可维护优于功能多。

**北极星指标**：每月被扫描的独立仓库数（去重）。它同时反映"有没有人用"与"是否持续用"，
比 star 更接近真实价值。

**分阶段目标**

| 阶段 | 时间 | 产品目标 | 社区目标 | 量化验收 |
| --- | --- | --- | --- | --- |
| 打基础 | 0-3 个月 | 检查项 13 → 18；支持 `--repo` 远程扫描；测试覆盖率 ≥ 90% | 双语文档、贡献者阶梯、每两周一次 triage | star ≥ 30；外部贡献者 ≥ 2；issue 首次响应 ≤ 72h |
| 建闭环 | 3-6 个月 | 批量扫描 + 教师端汇总报告；GitHub Action 上线 | 2 门课程试用；发布 v1.0.0 | 接入仓库 ≥ 50；月扫描 ≥ 300；star ≥ 100 |
| 扩影响 | 6-12 个月 | 插件机制（entry points）；输出兼容 Scorecard JSON | 3-5 门课程采用；中文技术社区 3 篇以上介绍 | 月扫描 ≥ 1000；贡献者 ≥ 10；star ≥ 300 |
| 求持续 | 1-3 年 | 评分白皮书与案例库成型；形成 2-3 名核心维护者 | 移交学院开源社团，建立维护者轮值 | 课程采用 ≥ 10 门；年扫描 ≥ 2 万次 |

目标设定遵循三条原则：**可验证**（每个数字都有统计口径）、**有挑战但可达**
（对照同类学生项目的增长曲线）、**与北极星指标对齐**（不为 star 做与使用无关的事）。

### 2.3 定策略：五个方向的组合拳

| 方向 | 关键动作 | 衡量指标 | 投入占比 |
| --- | --- | --- | --- |
| 产品 | 插件化架构；检查项分"基础/进阶"两级；`--repo` 远程扫描；教师端汇总报告；一键生成修复建议 | 检查项数、扫描成功率、平均扫描耗时 | 40% |
| 社区 | good first issue 常备 5 个以上；贡献者阶梯（用户→报告者→贡献者→评审者→维护者）；双语文档；固定每月一个小版本 | 外部贡献者数、issue 响应时长、PR 合并周期 | 30% |
| 生态 | GitHub Action；pre-commit hook；SARIF 输出；与 Scorecard JSON 互转 | Action 安装量、CI 集成仓库数 | 15% |
| 合规与治理 | MIT + DCO（不用 CLA，降低贡献门槛）；语义化版本；SECURITY.md；行为准则 | 许可证识别率、发布节奏达成率 | 5% |
| 推广 | 课程作业场景合作；中文社区技术文章；开源之夏选题；校园行分享 | 文章阅读量、课程采用数、star 增速 | 10% |

**优先级判断**：先做"教学场景闭环"（批量扫描 + 汇总报告 + 作业模板），再做"生态集成"。
理由是前者的用户明确、反馈快，后者依赖前者积累的口碑。

**明确不做的事**（战略的一半是放弃）：

- 不做 Web UI：维护成本高，与"轻量 CLI"的定位冲突；
- 不做企业级合规报告：销售与法务门槛超出单人能力；
- 不做"检查项数量竞赛"：不可持续，也守不住；
- 不接商业广告与付费墙：会破坏"零依赖、可离线"的信任基础。

## 4. 风险与对策

| 风险 | 概率 | 影响 | 对策 | 预警信号 |
| --- | --- | --- | --- | --- |
| 单人维护导致长期停滞 | 中 | 高 | 模块化降低门槛；写清维护者交接文档；固定每月 triage | 连续 6 周无 commit |
| 被 Scorecard / GitHub 功能覆盖 | 中 | 中 | 绑定教学场景与中文生态，做平台不做的"脏活" | 平台上线可配置权重与建议生成 |
| 评分标准被质疑主观 | 高 | 中 | 公开权重与判定规则；提供教学版/严格版两套预设；允许完全自定义 | issue 中出现"为什么扣分"的争议 |
| 检查误判伤害信任 | 中 | 高 | 测试覆盖边界；误报反馈模板；48h 内修复误报 | 同一检查项连续被报告误判 |
| 课程结束项目废弃 | 高 | 高 | 移交学院开源社团；设定最低维护承诺；寻找共同维护者 | 学期末提交量骤降 |
| 合规判断越界（给法律建议） | 低 | 高 | 明确"不构成法律意见"；只做事实提示与通用建议 | 用户要求"帮我判定是否侵权" |

## 5. 衡量与复盘

**季度 OKR（示例）**

| 目标 | 关键结果 | 当前 | 目标 |
| --- | --- | --- | --- |
| O1 教学场景闭环 | KR1 接入课程的班级数 | 0 | 2 |
| | KR2 批量扫描覆盖仓库数 | 0 | 500 |
| O2 社区初步形成 | KR1 外部贡献者数 | 0 | 3 |
| | KR2 issue 首次响应中位数 | — | ≤ 72h |
| O3 工程质量 | KR1 测试覆盖率 | 约 88% | ≥ 90% |
| | KR2 自检评分 | 100 | ≥ 95 |

**复盘机制**：每月最后一个周五做一次 30 分钟看板复盘（北极星、issue 响应、发布节奏）；
每季度重跑一次「五看三定」，更新假设——尤其是"竞争"与"机会"两节，因为它们变化最快。

**需要持续观察的三个信号**：教学场景的真实采用率、GitHub Action 的安装量、
平台方（GitHub / OpenSSF）的产品动向。任何一个信号恶化，都应当触发战略调整而不是
"再发一个版本试试"。

## 6. 结语：三个判断

1. **小工具的价值不在功能多，而在把模糊的规范变成可执行的动作。** "补一个 LICENSE"
   比"阅读十篇开源治理文章"更容易被真正执行。
2. **战略控制点不是功能清单，而是场景标准。** 决定项目能走多远的，是有多少人的工作流
   里嵌入了它，而不是它有多少个检查项。
3. **学生项目的可持续性取决于能否交给社区。** 从第一天起就按"别人能接手"的标准写文档、
   写测试、写贡献指南，比任何增长技巧都重要。

从这个角度看，这个项目的期末作业不是终点，而是它第一次公开接受真实用户的检阅。
评分卡量的是仓库，五看三定量的是方向——两者都要可解释，也都需要持续迭代。
